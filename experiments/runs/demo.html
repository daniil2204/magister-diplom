Цілі за класом вразливості (SWC)

Класи вразливостей

SC01 Контроль доступу

Привілейовану дію (зміна власника, selfdestruct, адреса реалізації) може виконати будь-хто, бо вона не захищена перевіркою msg.sender — або захищена через tx.origin, який підробляється.

Загроза: Зловмисник стає власником контракту чи знищує його та виводить усі кошти.

SC06 Неперевірений виклик

Результат низькорівневого виклику (call / send) не перевіряється, і виконання триває так, ніби переказ відбувся успішно.

Загроза: Кошти вважаються надісланими, хоча переказ міг не пройти — втрата коштів або неузгоджений стан.

SC08 Повторний вхід (reentrancy)

Зовнішній виклик передає керування зловмиснику ДО того, як оновиться стан (баланс), і той рекурсивно викликає ту саму функцію знову, доки стан ще старий.

Загроза: Виведення набагато більше коштів, ніж належить, — класична атака на The DAO (2016).

SC09 Переповнення цілого

Арифметичне переповнення або від'ємне переповнення (до Solidity 0.8 операції не мають вбудованих перевірок меж).

Загроза: Баланс «обертається» на величезне число — безпідставне збагачення чи обхід перевірок меж.

SC10 Delegatecall

Делегований виклик за адресою, яку задає зловмисник: чужий код виконується у контексті (сховищі) цього контракту.

Загроза: Повне захоплення контракту — зловмисник переписує будь-яку змінну, зокрема власника.

Як читати результати

Вердикти

Підтверджено — Знайдено конкретний вхід (контрприклад), що реалізує вразливість. Реальна загроза.
Спростовано — Статичний етап позначив місце як підозріле, але символьне виконання довело, що ЖОДЕН вхід не може реалізувати атаку (захищено, напр., nonReentrant або require). У цьому місці вразливості немає.
Не визначено — За відведений бюджет вирішити не вдалося: таймаут або непідтримувана конструкція.

Колонки таблиці

  • Клас — Клас вразливості за класифікацією SWC та його підтип.
  • Функція:рядок — Де саме в коді розташована ціль — функція і номер рядка.
  • Вердикт / контрприклад — Результат символьного етапу. Для «Підтверджено» наведено контрприклад — конкретний вхід (функція, sender, аргументи), яким відтворюється атака.
  • R — Ризик R(t) ∈ [0;1] (формула 2.16): критичність класу × контрольованість × незахищеність × наявність цінностей. Наскільки серйозна ціль.
  • P — Пріоритет P(t) ∈ [0;1] (формула 2.17): ризик R, зважений на складність перевірки (кількість розгалужень). Визначає порядок цілі в черзі аналізу.

Що тут вразливе і чому. Контракт спершу надсилає кошти зовнішній адресі, а баланс обнуляє ЛИШЕ ПОТІМ. 1// Paired fixed version of Vault.sol: reentrancy lock.
2// Compile with solc 0.8.x (tests pin 0.8.20).
3// Expected targets: exactly ONE RE target -- the write `balances[msg.sender] = 0` after the
4// call. It must be REFUTED: a second-level entry into any public function reading or writing
5// `balances` is unsat because `locked == true` at the moment of the call.
6//
7// The write `locked = false` in the modifier tail also follows the call and matches the static
8// rule for SC08, but a lock variable never produces an RE target: it is the protection
9// mechanism, not the flaw. Otherwise every `nonReentrant` would add one spurious target per
10// function, and a target the symbolic stage did not reach in time would be a false positive in
11// moderate mode.
12//
13// Control values:
14// E_t = {call address, value} = {msg.sender, amount} -> A = 1/2 = 0.5
15// g = 1 (the lock check require(!locked) dominates the target) -> D = 1/(1+1) = 0.5
16// M = 1 (the entry point transfers ether)
17// R = 1.0 * (0.4*0.5 + 0.4*0.5 + 0.2*1.0) = 0.6
18// b = 3 (require(!locked), require(amount > 0), require(ok))
19// P = 0.6 * 4^(-0.5) = 0.3
20pragma solidity ^0.8.0;
21 
22contract VaultFixedGuard {
23 mapping(address => uint256) public balances;
24 bool private locked;
25 
26 modifier nonReentrant() {
27 require(!locked);
28 locked = true;
29 _;
30 locked = false;
31 }
32 
33 function deposit() external payable { balances[msg.sender] += msg.value; }
34 
35 function withdraw() external nonReentrant {
36 uint256 amount = balances[msg.sender];
37 require(amount > 0);
38 (bool ok, ) = msg.sender.call{value: amount}("");
39 require(ok);
40 balances[msg.sender] = 0;
41 }
42}

1// SC08 + SC06 fixture with a real IF on the path to the target.
2//
3// Modelled on SimpleDAO from the `reentrancy` category of SmartBugs Curated; the original was
4// downloaded and compared line by line. Two deliberate departures from it, both reported to the
5// author before this file was written:
6//
7// 1. The original is `pragma solidity ^0.4.2`, where ALL arithmetic is unchecked. Ported to
8// 0.8 so that the fixture carries exactly the two targets it is meant to isolate; under
9// 0.4 it would also carry two SC09 targets (see the note at the bottom).
10// 2. `queryCredit` is dropped: it is a view function and produces no target of any class.
11//
12// Everything that matters is kept: the guard is an `if`, not a `require`; the call result is
13// ignored; the storage write happens after the call; and -- unlike Vault.sol -- the transferred
14// amount comes from an ARGUMENT, not from storage. That last point is why A = 1 for RE here and
15// A = 0.5 in Vault, which is what makes this fixture a check that the numbers are computed
16// rather than copied.
17//
18// Expected targets: exactly TWO, both on the SAME node -- the write `credit[msg.sender] -= amount`
19// after the call. The target is the write, not the call (see "RE and UC" in CLAUDE.md).
20//
21// RE (SC08):
22// E_t = {call address, value} = {msg.sender, amount}; msg.sender is in X_env and amount is
23// in X_arg, so both are controlled -> A = 2/2 = 1.0
24// V_auth = {} and `credit` is a mapping, so it is not a lock variable: g = 0 -> D = 1.0
25// M = 1.0 (the entry point calls with value and writes mapping(address => uint))
26// S(RE) = 1.0
27// R = 1.0 * (0.4*1.0 + 0.4*1.0 + 0.2*1.0) = 0.4 + 0.4 + 0.2 = 1.00
28// b = 1 (the IF node; there is no require anywhere) -> P = 1.00 * 2^(-0.5) ~= 0.7071
29// CONFIRMED: the callee re-enters `withdraw` while `credit[msg.sender]` still holds the old
30// value, because the subtraction happens only after the call returns.
31//
32// UC (SC06):
33// E_t = {call address, call arguments} = {msg.sender, ""}; the empty bytes literal is a
34// constant and is not controlled -> A = 1/2 = 0.5
35// g = 0 -> D = 1.0, M = 1.0, S(UC) = 0.6
36// R = 0.6 * (0.4*0.5 + 0.4*1.0 + 0.2*1.0) = 0.6 * 0.8 = 0.48
37// b = 1 -> P = 0.48 * 2^(-0.5) ~= 0.3394
38// CONFIRMED: `res` is never read, so the path with res = false reaches the write.
39//
40// donate: ZERO targets. In 0.8 `+=` is checked, so it is no SC09 target, and there is no call.
41//
42// Under the original 0.4.2 pragma there would be two more targets, both SC09:
43// `credit[to] += msg.value` (CONFIRMED -- msg.value is unbounded in the model, so the sum
44// overflows for every storage state in D) and `credit[msg.sender] -= amount` (REFUTED -- the IF
45// puts credit[msg.sender] >= amount into PC).
46pragma solidity ^0.8.0;
47

49 mapping(address => uint256) public credit;
50 
51 function donate(address to) public payable {
52 credit[to] += msg.value;
53 }
54 
55 function withdraw(uint256 amount) public {
56 if (credit[msg.sender] >= amount) {
57 (bool res, ) = msg.sender.call{value: amount}("");
58 credit[msg.sender] -= amount;
59 }
60 }
